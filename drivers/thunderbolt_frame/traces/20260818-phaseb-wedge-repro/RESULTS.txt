CONCLUSION: the reload-under-saturation wedge survives every software
ordering (v0..v7). All seven iterations produced real, KUnit-pinned
hygiene fixes (READY gate, quiesce ordering, BYE handshake, dispatch
fences, kick semantics, device-leak fix), but the trigger is below
software: tearing down a SATURATED session on this Maple Ridge pair
sometimes leaves the reloading side's router egress permanently
credit-dead -- same phenomenology as the known Intel "passes a saturated
run then wedges newly created rings" behavior (spec s6) that motivated
keeping hardware E2E off. Discriminators run while wedged: fresh HopID
(dead), fresh NHI ring index via a ring-holder module (dead), full
hop-entry/ring re-programming (dead), either-end reboot / PHY bounce
(alive). No deactivation-timeout or config-space evidence exists; the
state is invisible to software.

Operational guidance: never hot-reload tbrxe/tbframe while RDMA traffic
is running (quiesce clients first -- idle reloads have been consistently
safe all day); a wedge is cleared by rebooting the node whose TX ring
shows posted-but-unconsumed descriptors (tools/nhi-ring-regs.py).
Next diagnostic steps if the class must die completely: NHI register
diff via the tbdma tooling across a wedge, testing whether a
tb_switch_reset / lane retrain clears it without reboot, and asking
Intel about post-saturation credit teardown on Maple Ridge.
